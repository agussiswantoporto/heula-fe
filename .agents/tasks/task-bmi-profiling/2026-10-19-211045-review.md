# Mandatory BMI profiling step with safety-preserving recommendation adjustment

Adds a mandatory BMI step to the Heula onboarding (Welcome → Goal → Exercise → **BMI** → Recommendation), a framework-free `src/lib/bmi.ts` with Asia-Pacific thresholds, a pure post-process layer that folds BMI into the recommendation engine without weakening any safety invariant, and a guarded BMI card on Stats. The work lands as four commits (`cf7fafa`, `0e4cae7`, `b547750`, `7daf0e8`) over base `4f80689`, touching exactly ten `src/` files and no infrastructure. BMI classification only ever softens the primary method or sharpens framing — the heavy-exercise guard still returns before any BMI logic, and `canOfferAggressive` remains the sole gate for aggressive methods.

Watch for: nothing blocking. The only observations are informational — `copy.onboarding.bmiQuestion` is added but unused (BmiStep reads `copy.bmi.stepTitle`), and the two eslint warnings surfaced by the build are both pre-existing (confirmed).

**Verdict**: APPROVED

## High-level view

The BMI math lives in a new pure `src/lib/bmi.ts` with the exact Asia-Pacific cut-offs (underweight <18.5, normal 18.5–22.9, overweight 23–24.9, obese ≥25), a divide-by-zero/non-finite guard that returns `NaN`, and a `bmiCategory` that maps `NaN` to `"normal"` so a transient bad value can never trigger a strict adjustment. `ProfilingAnswers` gains mandatory `heightCm`/`weightKg`, and every construction site (both OnboardingFlow literals, the recommendation test helper, and the two inline test literals) was updated so strict compilation holds.

The recommendation engine folds BMI in as a post-process (`applyBmiAdjustment`) applied after the goal switch resolves `base`. The three safety invariants hold: the R1 heavy branch returns 14:10 + a non-null warning before BMI runs, `canOfferAggressive` is untouched and stays the only path to 20:4/omad, and the adjustment only reorders methods already present — it never adds an aggressive one. Underweight softens the primary to 14:10 when stricter, strips 18:6/20:4/omad from alternatives, and always carries the caring note; overweight/obese only reorders 18:6 forward for weight-loss users who already qualify, never jumping the primary.

The onboarding gains a mandatory `BmiStep` with two bounded numeric inputs, a live numeric BMI, category label and one-liner, an animated four-segment gauge built from semantic Tailwind tokens, and the rough-indicator/not-medical-advice disclaimer. Advancement is gated both by the disabled Lanjut button and a hard guard on `goNext` at the BMI index. `TOTAL_STEPS` is 5 in the right order, and rerun mode prefills stored height/weight through useState initializers. Stats adds a BMI card that reads the stored profiling, guards with `isValidBmiInput`, and renders nothing for older profiling that predates the fields.

Verification was run independently: `npx tsc --noEmit` is clean, `npx vitest run` reports 185 passing across 8 files (including the no-emoji scan over 70 files and the BmiStep), and `npm run build` succeeds.

### BMI library: thresholds, guards, and the NaN-as-normal default

`src/lib/bmi.ts` is framework-free (no React import) and matches the pure-lib conventions. `computeBmi` returns `NaN` when either input is non-finite or `heightCm <= 0`, which closes the divide-by-zero case before the division runs. `bmiCategory` applies the Asia-Pacific cut-offs exactly — the boundary tests pin 18.49→underweight, 18.5→normal, 22.9→normal, 23.0→overweight, 24.9→overweight, 25.0→obese — and maps `NaN` to `"normal"`. That last choice is the keystone of the safety story downstream: a half-filled or malformed BMI resolves to the no-op category, so an invalid value can never push a user toward a stricter method.

### Recommendation post-process preserves every safety invariant

`applyBmiAdjustment(base, category, answers)` runs after `switch(goal)` produces `base`, and the ordering is what makes it safe. The R1 heavy guard (`answers.exercises && answers.intensity === "heavy"`) returns `buildHeavy()` — 14:10 with a non-null warning and `["16:8"]` alternatives — before any BMI code executes, so a heavy exerciser is never BMI-adjusted regardless of category. The dedicated test iterates every goal with underweight (45kg) and obese (80kg) inputs and confirms 14:10 + non-null warning + `["16:8"]` every time.

`canOfferAggressive` is unchanged and remains the sole gatekeeper. The underweight branch recomputes the primary from `NON_GENTLE` membership (anything other than 14:10 softens to 14:10), filters `UNDERWEIGHT_FORBIDDEN` (18:6/20:4/omad) out of alternatives, and unconditionally sets `warning` to the caring note plus a caring rationale prefix — so the note surfaces for every goal, not just the ones that would already warn. The overweight/obese branch is explicitly fenced: it returns `base` unless `goal === "weight_loss" && canOfferAggressive(answers)`, and even then it only pulls an already-present 18:6 to the front and appends firmer framing. It never changes `base.method` and never adds a method, so the primary can never auto-jump to 20:4/omad. The `normal` branch returns `base` by reference, which the direct unit test asserts with `.toBe(base)`.

The test suite nails the invariants directly rather than by proxy: underweight across every goal never primes 18:6/20:4/omad and always warns; overweight/obese + weight_loss + none/light keeps 16:8 primary with 18:6 reordered to `alternatives[0]`; and a heavy weight-loss user surfaces no aggressive alternative despite `exerciseState` mapping heavy→none at the predicate level, because the R1 guard returns first.

### BmiStep: gating, accessibility, and the live gauge

The step disables Lanjut until `isValidBmiInput(heightCm, weightKg)`, and `OnboardingFlow.goNext` independently returns early at `BMI_STEP` unless the same predicate passes — advancement is gated in two places. Inputs use `inputMode="numeric"` (height) and `"decimal"` (weight) with `min`/`max` from the bmi.ts bounds, `min-h-12` targets (≥44px), `focus-within:border-brand` for a visible focus ring, and `useId`-generated `aria-describedby` wiring each input to its validation message with `aria-invalid`. Validation text shows only when a value is present but out of range, so an empty field isn't flagged prematurely. `parseField` maps empty string to `null` and keeps state SSR-safe (no window access).

The gauge is pure markup: four flex segments sized from the Asia-Pacific spans mapped onto a clamped 15–35 display range (so 18.5/23/25 land on segment edges), colored with semantic tokens (`content-muted/35`, `brand`, `brand-soft`, `danger`) that resolve in both light and dark, and a `motion` spring-animated marker positioned by `markerPercent`. No chart library, no emoji — the no-emoji scan covers this file and passes.

### Stats card guard for pre-BMI profiling

`StatsOverview` reads `profiling?.heightCm`/`weightKg` and gates the card on `heightCm !== undefined && weightKg !== undefined && isValidBmiInput(...)`. Older persisted profiling that predates the mandatory fields resolves `hasBmi` to false and the card renders nothing — no crash, no `NaN` leak into the UI. The same guard governs the single read site, so there's no second unguarded access.
