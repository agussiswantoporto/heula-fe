# Implementation Plan — SW-based reminders, permission/status UI, iOS install prompt

Scope: upgrade Heula's reminder subsystem so notifications fire from the Service Worker (survive the app being closed, best-effort), with a graceful in-page fallback, a permission/status UI on the Profile (settings) screen, and an iOS install-to-Home-Screen prompt. Edit in place (no worktree). Stack/versions unchanged.

## Design decisions (made here, grounded in the code I read)

- **SW message protocol lives in `src/app/sw.ts` next to the existing Serwist setup.** The file already has `declare const self: ServiceWorkerGlobalScope` and `serwist.addEventListeners()`. I add a separate `self.addEventListener("message", ...)` AFTER `serwist.addEventListeners()` so Serwist's own message handling (SKIP_WAITING etc.) is untouched; my handler only acts on namespaced `heula/*` types and ignores everything else. Rationale: a dedicated listener with namespaced types is the lowest-risk way to coexist with Serwist (Serwist does not own the `heula/` namespace), and keeps precache/offline intact.
- **Message types are namespaced string literals:** `"heula/schedule-reminder"` and `"heula/cancel-reminder"`. Rationale: avoids collisions with Serwist's internal messages and makes the grep-verification check (`grep heula/schedule-reminder public/sw.js`) meaningful.
- **SW arms a `setTimeout` keyed by reminder kind (`"end"` | `"start"`) in a module-scope `Map`.** On fire it calls `self.registration.showNotification(title, { body, tag, ... })`. `tag` = the kind, so a re-schedule replaces rather than stacks. Rationale: mirrors the existing in-page per-kind timer model (`timers.end` / `timers.start`) so behavior is consistent across both paths; `showNotification` is the only notification API available inside a SW.
- **`notifications.ts` keeps its exact exported surface** (`PermissionStatus`, `ScheduleStatus`, `isSupported`, `getPermission`, `requestPermission`, `scheduleEndReminder`, `scheduleStartReminder`, `clearScheduled`) and routes **SW-first, in-page fallback** internally. Rationale: the three call sites (`useAppStore`, `TimerControls`, `FastingTimer`) import these by name and must keep working unchanged.
- **"SW-first" is best-effort and non-blocking.** `scheduleEndReminder` / `scheduleStartReminder` stay **synchronous** returning `ScheduleStatus` (call sites use the sync return). The SW post is fire-and-forget via a `void`-returning helper that resolves `navigator.serviceWorker.ready`; if no controller/registration or `showNotification` is unavailable, the in-page `setTimeout + new Notification()` path runs as it does today. We always also keep an in-page timer as a backstop only when the SW path is NOT taken (not both, to avoid double-fire). Rationale: honest best-effort; keeps the public API synchronous as the call sites expect.
- **`clearScheduled()` cancels BOTH** paths: posts `heula/cancel-reminder` for each kind to the SW and clears any in-page timer. Rationale: a user may have scheduled via SW on one session and we must be able to cancel it regardless of which path armed it.
- **iOS/standalone detection is a small pure, SSR-safe helper in `src/lib/pwa.ts`** (new file in the lib layer, matching the "pure/typed helpers in src/lib" convention). Rationale: keeps `window`/`navigator` guards in one tested place; `ReminderSettings` stays a thin client component.
- **README "Pengingat" section is reworded** to match the new behavior (SW-based, best-effort, survives close when installed). The no-emoji vitest scans `src/` only (confirmed: `SRC_ROOT = join(here, "..", "..")` -> `src/`), so README is not under the scan, but we keep it emoji-free regardless and consistent with the UI copy.

Note on an assumption: Serwist (`@serwist/next`) auto-registers the generated `public/sw.js` in production builds (default `register: true`), and `src/app/sw.ts` sets `clientsClaim: true` + `skipWaiting: true`, so an active controller is available after the first load. No manual registration code is added. If, during implementation, `navigator.serviceWorker.controller` is reliably null on first paint, use `navigator.serviceWorker.ready` (the active registration) for posting — the plan already routes through `ready`.

## Steps

- [ ] 1. Add the SW message protocol + handler in the service worker.
      In `src/app/sw.ts`, AFTER `serwist.addEventListeners()`, add a module-scope `Map<"end"|"start", ReturnType<typeof setTimeout>>` and a `self.addEventListener("message", ...)` that handles two namespaced types: `"heula/schedule-reminder"` (payload `{ type, kind: "end"|"start", fireAtMs: number, title: string, body: string }`) and `"heula/cancel-reminder"` (payload `{ type, kind: "end"|"start" }`). On schedule: clear any existing timer for that kind, compute `delay = fireAtMs - Date.now()`, and if `delay > 0` set a `setTimeout` that calls `self.registration.showNotification(title, { body, tag: kind, badge/icon from /icons, requireInteraction: false })` and deletes the map entry; if `delay <= 0` ignore. On cancel: clear and delete the timer for that kind. Ignore any message whose `data?.type` does not start with `"heula/"`. Add honest comments: SW `setTimeout` only survives while the OS keeps the SW alive (best-effort, not a guaranteed native alarm), and that integrating with the native phone Alarm/Clock app is impossible for a PWA — web notifications only.

## Notes / known gaps

- The task text says the no-emoji scan covers "src + README", but the actual test (`src/lib/__tests__/no-emoji.test.ts`) scans `src/` only. Step 7 keeps README emoji-free regardless, so either interpretation passes.
- SW `setTimeout` reliability is bounded by the OS/browser keeping the worker alive; this is the honest best-effort ceiling and is documented in code comments and the README. No push server / VAPID / native alarm is introduced (out of scope and impossible for a PWA).
- Double-fire avoidance: when the SW path is used we deliberately do NOT also arm an in-page timer. If a future requirement wants belt-and-suspenders delivery, the in-page `tag`-based de-dupe would need coordinating; out of scope here.
