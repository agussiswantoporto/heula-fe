# Heula PWA — final acceptance review

Heula is a client-only Next.js 15 fasting tracker: onboarding profiling drives a pure recommendation engine, a persisted Zustand store holds live/profile/settings state, Dexie owns durable history, and Serwist supplies the installable offline shell. This pass checks the whole tree against the 20 acceptance criteria, faithful implementation of design.md, and the two MEDIUM design-review findings. The build is green (zero TS errors), 148 Vitest tests pass across 6 suites, lint reports 0 errors, and both the emoji and icon sweeps come back clean. Both MEDIUM findings are resolved in code exactly as specified. Watch for: nothing blocking — the two eslint warnings (`_exhaustive`, `_planLabel`) are intentional sentinels, not defects (confirmed).

**Verdict**: APPROVED

## High-level view

The recommendation engine is the behavioral core and it matches the design table row-for-row. Finding 1 lives here: the aggressive-method gate is encoded as `canOfferAggressive = goal === "weight_loss" && (exerciseState === "none" || "light")`, keyed on the total `exerciseState` classifier rather than the malformed boolean prose from design Section 6.3. Heavy exercise is caught by an early guard that always returns `14:10` with a mandatory warning, so `20:4`/`omad` can only ever surface as R2/R3 alternatives and never as the recommended method. The test suite enumerates all 16 rows plus the full 25 raw-input product, including the degenerate `exercises:true/intensity:null` state.

Finding 2 is split correctly across onboarding and settings. The onboarding method list is `METHOD_ORDER.filter(id => id !== "custom")`, so custom is unreachable where its hours would be undefined; custom becomes selectable only in `PlanPicker`, which owns the 8..23 clamped hours input. `customFastingHours` carries a defined store default of 16, so no path lands on an undefined custom target.

The persisted store shape matches design Section 8 exactly: the `partialize` whitelist persists the eight domain keys and deliberately excludes the transient `hydrated` flag, which is set only from the `onRehydrateStorage` completion callback. `startFast`/`stopFast` snapshot `targetHours`/`planLabel` from the store (never the catalog placeholder) and are the only places the store touches Dexie.

The PWA infra is wired per design: `sw.ts` is verbatim with the single `serwist.addEventListeners()` call, the manifest references four valid PNGs with correct `any`/`maskable` purposes, and the build emits `public/sw.js`. The two hard constraints hold mechanically — a repo-wide emoji scan finds nothing, and ESLint bans every icon import except `react-icons/io5` plus server-side imports of the Dexie layer.

### Finding 1 — aggressive-method gate keyed on exerciseState

`recommendation.ts` encodes the invariant as the design-review correction prescribes (confirmed):

```ts
export function canOfferAggressive(answers: ProfilingAnswers): boolean {
  const canOfferAggressive =
    answers.goal === "weight_loss" &&
    (exerciseState(answers) === "none" || exerciseState(answers) === "light");
  return canOfferAggressive;
}
```

The malformed `&& (...) while exercises is false OR intensity is null/"light"` prose from design Section 6.3 was not transcribed. `exerciseState` collapses `exercises:true/intensity:null` to `"none"`, so weight-loss + the degenerate state correctly surfaces the aggressive alternatives (intended R2 behavior). Heavy exercise returns from `buildHeavy()` before the goal switch, yielding `14:10` with `alternatives: ["16:8"]` and a non-null warning — `20:4`/`omad` are structurally unreachable for heavy exercisers. R2/R3 are the only rows whose alternatives contain `["18:6","20:4","omad"]`; R4 (moderate) drops to `["18:6"]`. This satisfies AC6 and FR11.3 at the data level.

### Finding 2 — custom excluded from onboarding, owned by PlanPicker

`RecommendationStep.tsx` builds its list from `METHOD_ORDER.filter(id => id !== "custom")` (confirmed), so onboarding can never select a custom plan with undefined hours. `PlanPicker.tsx` is the sole custom entry point and clamps input to 8..23 before writing. `useAppStore` defines `customFastingHours: 16` in `INITIAL_STATE`, closing the degenerate target gap that Finding 2 and NIT 4 flagged.

### Store shape and persistence

The `partialize` return is typed `PersistedState` and lists exactly the eight whitelisted keys — `hydrated` is absent (confirmed), so a stale `hydrated:true` can never rehydrate ahead of the current cold load and defeat the guard. `startFast`/`stopFast` resolve `targetHours`/`planLabel` from store state via `resolveTargetHours`/`resolvePlanLabel`, so a custom fast never silently uses the catalog placeholder 16.
